# Atlas: воспроизводимые нагрузочные прогоны

Стенд находится в `profile*_test.go`; в обычном запуске и обычных тестах отключён. Рабочая `data/` не используется. Сервер запускается отдельным процессом, браузеры — с временными профилями. Инструментация клиента добавляется только HTTP-обёрткой тестового сервера. Публичных диагностических маршрутов в Atlas нет.

```powershell
$env:ATLAS_CHROME='C:\Program Files\Google\Chrome\Application\chrome.exe'
$env:ATLAS_PROFILE='C:\projects\my-game\profiling\after'
go test -run '^TestProfileAtlas$' -count=1 -timeout 30m -v
go test -run '^TestProfileTransfer$' -count=1 -timeout 5m -v
```

Для повторения без долгой подготовки трёх крупнейших карт задайте `ATLAS_PROFILE_SKIP_MAPS=1`. Карта 4096×4096 всё равно подготавливается. Для полного прогона удалите эту переменную.

## Артефакты и ограничения метода

- `before/`: первая итерация измерений; сохранены исходники производственного кода. Подготовка карт и одноклиентские сценарии валидны. Начиная с `2000_tokens_3_clients_move`, результаты первого клиента **невалидны**: фоновые вкладки Chrome приостановили rAF. Нулевой FPS там нельзя считать пределом Atlas.
- `before-corrected/`: исходный Atlas, но каждый клиент в отдельном процессе Chrome. Стенд проверяет, что каждый клиент действительно рисовал кадры.
- `after/`: промежуточный полный повтор после исправлений, включая все большие карты. В финале дополнительно исправлены округление нечётных размеров и пересоздание графики при зуме.
- `after-corrected/`: окончательный код, повтор с `ATLAS_PROFILE_SKIP_MAPS=1`, как в `before-corrected/`.
- `hardware.json`: CPU и установленная RAM. GPU/версия Chrome/параметры запуска находятся в `results.json`.
- `results.json`: сырые измерения каждого сценария, каждого клиента и серверного процесса.
- `*.cpuprofile.json`: результат Chrome Profiler.stop (сам CPU-профиль лежит в поле `profile`).
- `server.*.pprof`: CPU, heap, mutex, block профили Go; анализ через `go tool pprof -top файл`.
- `upload-transfer.json`: отдельное чтение HTTP-тела и подготовка/сохранение карты. Валидный JPEG 4096×4096 дополнен байтами до 256 МиБ минус 1 байт; это проверка предела загрузки, а не реалистичная степень сжатия.

FPS — число реальных вызовов отрисовки за измеренный интервал; время кадра — CPU-время функции draw, а не время GPU. В тесте `render` включён постоянный рендер. Профилировщик и сбор метрик имеют небольшой расход и одинаково используются до/после.

RAM браузеров — сумма Windows Private Bytes/Working Set процессов **всех тестовых браузеров**, включая GPU и служебные процессы; Working Set может повторно учитывать общие страницы. JS heap, ImageBitmap и IndexedDB измеряются отдельно. RAM/CPU сервера относятся к отдельному процессу без генератора карт и драйвера теста; CPU% задан относительно одного ядра, не всего 12-поточного CPU.

HTTP — `Network.loadingFinished.encodedDataLength`; кэшированные ответы могут иметь нулевой переданный объём. WebSocket — UTF-8 байты полезной нагрузки, без TCP/TLS-заголовков. Задержка движения — от отправки координаты до первого draw с полученной актуальной координатой; промежуточные обновления между кадрами могут быть пропущены. Это loopback на одном компьютере, не WAN. Подготовка карт включает чтение HTTP-тела, нарезку, сжатие и запись; отдельный тест уточняет составляющие.

Камера/зум в длительном сценарии меняются 3 минуты, по шести 30-секундным интервалам. Это короткий soak-тест, а не доказательство устойчивости многочасовой игры. Изначальные HTTP-кэши браузеров чистые; внутри одного прогона они сохраняются между сценариями. Карты — детерминированные подробные JPEG; иные форматы и визуальная структура могут давать другие результаты. CPU/GPU ноутбука, температура и фоновые программы влияют на цифры.
