Scene data, asset discovery и большие сцены
Не считать lazy loading только отложенной загрузкой бинарных файлов.
Архитектура должна избегать передачи клиенту данных, которые ему пока не нужны, включая metadata и identifiers ресурсов.
Различай три уровня:
Campaign asset catalog.
Assets, используемые конкретной Scene.
Assets, необходимые клиенту для текущего загруженного/видимого состояния Scene.
Эти множества не должны автоматически передаваться клиенту целиком.
Campaign entry
При входе в Campaign клиент получает только минимальные сведения, необходимые для отображения доступных Scenes.
Player получает summaries опубликованных Scenes.
GM получает summaries всех Scenes.
Получение списка Scenes не должно загружать:
state этих Scenes;
их objects;
revisions;
asset manifests;
список asset ids/hashes;
binary assets.
Не загружай данные всех опубликованных Scenes заранее.
Campaign Asset Store
Assets принадлежат Campaign и могут совместно использоваться несколькими Scenes.
Campaign-level ownership не означает, что клиент при входе получает полный каталог Campaign assets.
Обычный Player не должен получать полный список:
asset ids;
filenames;
hashes;
MIME types;
sizes;
URLs;
другую asset metadata,
если эти сведения не требуются для загруженного состояния доступной ему Scene.
Интерфейс asset library для GM является отдельным use case и может получать каталог независимо, желательно с pagination/search при потенциально большом количестве ресурсов.
Scene opening
Открытие Scene не должно автоматически означать загрузку Campaign asset catalog.
Asset должен обнаруживаться клиентом через фактически загруженное состояние Scene.
Если объект ссылается на asset, клиент получает необходимую ссылку/identifier вместе с этим объектом либо посредством отдельного asset-resolution запроса.
Binary asset загружается только тогда, когда он действительно требуется клиенту.
Не создавай обязательный full-scene asset manifest, если он заставляет клиента узнать обо всех assets большой Scene до того, как они понадобились.
Large Scenes
Не предполагай, что state Scene всегда достаточно мал для полной передачи при каждом открытии.
Архитектура должна позволять большой Scene загружаться пространственно частями.
Для больших Scenes сервер должен иметь возможность определить, какие scene objects/state относятся к необходимой клиенту области.
Не фиксируй заранее конкретную структуру данных вроде quadtree или R-tree, если существующий код не требует её. Выбери простейшую структуру, обеспечивающую требуемое поведение.
Клиент не должен обязательно получать object state всей огромной Scene только ради отображения небольшого viewport.
Предусмотри возможность:
initial loading области около текущего viewport;
догрузки данных при pan/zoom;
выгрузки или освобождения данных, которые долго не нужны;
небольшого bounded prefetch за пределами viewport.
Размер prefetch должен быть ограничен.
Asset loading follows scene loading
Asset discovery и asset loading должны следовать за загрузкой scene objects.
Если клиент ещё не получил объект из удалённой части Scene, ему обычно не требуется знать asset ids/hashes этого объекта.
Таким образом для большой Scene желательно избежать последовательности:
full Scene state
→ full Scene asset manifest
→ lazy binary asset loading.
Предпочтительная модель:
required scene regions/state
→ relevant objects
→ asset references этих объектов
→ необходимые asset metadata
→ необходимые binary resources.
Не оптимизируй отдельно передачу hashes, если клиент всё равно получает полное состояние всех объектов Scene: в таком случае сначала оцени, является ли full-scene state настоящим источником масштабирования.
Large map images
Большое background/map image не должно обязательно декодироваться клиентом целиком в полном исходном разрешении.
Оцени необходимость tiled representation / image pyramid / LOD для крупных карт.
Цель: viewport небольшого размера не должен требовать скачивания и декодирования всего изображения огромной карты в максимальном разрешении.
Не вводи сложную tile-инфраструктуру без оценки реальных размеров и текущей реализации, но не закладывай архитектурную зависимость от обязательного full-resolution decode.
Realtime and partial Scene state
Scene-local realtime subscription сохраняется.
Клиент получает realtime updates только для Scene, на которую сейчас подписан.
Если Scene поддерживает spatial/partial state, realtime-механизм также не должен заставлять клиента материализовать полное состояние Scene.
Revisioning должен позволять:
открыть Scene;
загрузить необходимое актуальное состояние;
уйти со Scene;
пропустить произвольное число промежуточных изменений;
вернуться;
восстановить актуальное необходимое состояние без обязательного проигрывания всей пропущенной истории.
Не вводи revision per chunk, event log или другую дополнительную сложность автоматически. Сначала адаптируй существующий reliable/revision механизм и выбери минимальное решение, обеспечивающее указанную семантику.
Fetch lifecycle
Scene/asset requests должны иметь ограниченный lifecycle.
При:
смене Scene;
быстром перемещении viewport;
disconnect;
уничтожении соответствующего объекта,
ненужные pending requests и subscriptions должны отменяться или переставать потреблять существенные ресурсы.
Одинаковые параллельные запросы одного asset желательно дедуплицировать.
Очередь загрузки должна иметь ограничение по concurrency и не должна неограниченно расти вслед за быстрым pan по большой Scene.
Client caches
Кэширование assets между Scenes допустимо и желательно, когда один ресурс используется повторно.
При этом:
decoded RAM cache должен быть bounded;
inactive decoded resources должны иметь lifecycle;
raw/browser/disk cache не должен предполагаться бесконечным;
переход на другую Scene не должен требовать немедленно выбрасывать полезный shared asset;
сам факт существования asset в Campaign не является причиной загрузить или декодировать его.
Permissions
Player не должен иметь возможность получить данные unpublished Scene через альтернативные endpoints.
Проверить отдельно authorization для:
Scene state;
scene objects/chunks;
asset metadata;
binary asset fetch.
Знание или угадывание asset id/hash не должно само по себе давать доступ к ресурсу unpublished или иначе недоступной пользователю Scene.
Shared assets and deletion
Удаление Scene не должно автоматически удалять Campaign asset, если он используется другой Scene.
Если будет реализована очистка orphaned assets, она должна учитывать все ссылки внутри Campaign и иметь явный безопасный lifecycle.
Performance invariants
Архитектура не должна иметь обязательных операций, стоимость которых при обычном просмотре одной Scene растёт:
со всеми assets Campaign;
со всеми Scenes Campaign;
со всеми objects других Scenes.
Для больших Scenes отдельно оцени операции, растущие с полным количеством scene objects/assets, и по возможности привязывай работу к реально необходимой клиенту части Scene.
Зафиксируй принятые решения и эти invariants в SCENES_HANDOFF.md, чтобы следующая модель не смогла случайно вернуть eager loading.
